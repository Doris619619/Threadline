# Windows 自动更新

## 0.1.4 版本说明

0.1.4 包含主窗口重新获得焦点和休眠恢复后的自动补查，以及只在发现新版时出现的轻量标题栏入口。下载完成不自动展开详情，由用户确认重启。

从 0.1.3 升级到 0.1.4 时，旧客户端仍使用原有更新提示；升级完成后才使用新的小型入口。安装包名称为 `Threadline_0.1.4_x64-setup.exe`，正式发布以 GitHub Release 的公开状态为准。

## 检查与交互

正式 NSIS 安装版在启动 30 秒后检查新版，持续运行每 6 小时再次检查。回到主窗口（包括从托盘恢复）或电脑休眠恢复时，距离上次实际检查至少一小时则补查；启动前 30 秒的焦点变化不提前触发。手动检查也计入冷却，但设置 → 关于 Threadline 的手动操作可以立即重试。频繁切窗不会反复请求更新源。

发现新版后，仅在完整工作台或工作站标题栏右侧显示小型“更新”入口，不增加横幅、额外行高或自动弹窗。点击入口才展开版本、下载进度与操作；外部点击、关闭按钮或 Escape 可关闭详情，入口仍保留。下载完成只将入口文字改为“重启更新”，不会自动展开，用户可以继续工作。

自动检查不会覆盖已发现、下载中、已下载或安装中的版本。点击后才下载，下载完成后用户确认重启才安装，普通退出不安装。失败保留当前程序，可以在详情或关于页重试。后台检查失败不会弹出全局错误框，可在关于页查看原因，下一次满足冷却的触发会重试。

### 提示位置与尺寸

按用户指定的 Codex 小型更新入口体验，使用标题栏内约 54–80px 宽、26px 高的文字与小图标，沿用桌面标题栏的鼠标操作密度。默认透明背景、无边框，不闪烁，不改变任务区域的尺寸。只有点击后才展开最多 280px 宽的详情浮层；窄工作站把浮层限制在窗口边缘以内。下载、重启等详情按钮保留至少 44px 点击高度。

[Chrome 的延后重启操作](https://support.google.com/chrome/answer/95414?co=GENIE.Platform%3DDesktop&hl=en)提供“由用户选择重启时机”的参考；入口尺寸是 Threadline 的适配值，不声称是 Codex 官方像素规格。

旧 0.1.0 没有更新逻辑，必须手动安装一次新版本。使用同一 appId、应用名称和 userData，保留已有登录与设备偏好。Web/PWA 不提供这个入口；目录 Preview 没有 NSIS 安装标记，只提示使用安装版。测试标记或更新配置不得手工写入交付目录包。

## 发布与配置

源码、NSIS 安装包、blockmap 和 latest.yml 统一位于公开的 `Doris619619/Threadline` 仓库，下载入口为 https://github.com/Doris619619/Threadline/releases/latest 。客户端匿名读取公开更新源，不包含 GitHub token 或 Supabase 管理员密钥。

源码仓库 Actions 需配置：

| 名称                                 | 类型     | 内容                         |
| ------------------------------------ | -------- | ---------------------------- |
| NEXT_PUBLIC_SUPABASE_URL             | Variable | 正式项目公开 URL             |
| NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY | Variable | 正式项目 sb_publishable_ key |

发布任务使用 GitHub Actions 自动提供的 GITHUB_TOKEN，仅 windows-release job 授予 contents: write；检查任务保持只读。不再需要个人 PAT 或跨仓库 Secret。

0.1.2 将更新源迁到 Threadline。未分发的旧 0.1.1 安装包不再使用；本机若已安装旧版，需手动覆盖安装 0.1.2，保留同一应用 ID 和数据目录。后续更新直接来自本仓库 Releases。

每次发布：

1. 修改 package.json 版本并完成 PR 审查与合并。版本必须递增，不覆盖已公开 Release。
2. 在要发布的提交创建匹配的 vX.Y.Z tag 并推送。手动 workflow 同样必须选择版本 tag。
3. Release workflow 校验版本，运行测试和 parity，使用正式 Supabase 公开配置构建；`desktop:release` 仅允许匹配 tag 的 GitHub Actions 执行。
4. 安装包完成本地验证后上传同一个草稿 Release，再下载比较三个资产，全部匹配才公开。失败保留草稿；修复后可重跑同 tag，已经公开则必须递增版本。

本地 `pnpm desktop:build` 和 Preview 均不上传文件。未公开的草稿不会被同学的客户端收到。需要修复坏版本时发布更高版本，客户端不自动降级。

## 实现边界

Main 管理更新状态和并发，Preload 仅向可信主窗口暴露读取、检查、下载、安装与订阅，不接受任意下载地址。状态带单调 revision，防止迟到读取覆盖下载进度。安装时保留正常 app.quit 生命周期，不能直接 app.exit 截断更新器。

Main 使用 Electron `browser-window-focus`（只接受主窗口）和 `powerMonitor.resume` 补查，退出时清除监听器和定时器。Renderer 的运行时负责状态订阅与安装保护，更新控件与标题栏入口分别承担操作和布局；Web/PWA 与 Edge 辅助窗口不挂载桌面更新入口。

云端非 GET/HEAD 请求以及任务队列计入保存保护。更新重启锁在用户点击确认时获取，有保存时拒绝安装；取消或安装失败后释放。锁期间不启动新云写入。此保护不自动提交尚未点击保存的表单，确认框会提示先完成编辑。

轻量标题栏入口的截图与本地验证见 [界面验证记录](screenshots/desktop-update/README.md)。

单元/界面测试、真实安装升级和线上更新源验证分别记录在 PR；只有用两个已安装版本走通下载和重启，才标记真实升级通过。新仓库尚无正式 Release 时，检查会显示可重试的网络/更新错误，不能据此声称线上更新已生效。

## 用户验收步骤

1. 运行 `Threadline_0.1.2_x64-setup.exe` 安装，使用安装后的快捷方式打开；不要使用 Preview 目录包。已有安装选择原目录，不卸载或清理数据。
2. 在设置 → 关于确认版本为 0.1.2；检查原登录状态、任务、项目仍在，修改一条可恢复的任务并等待保存完成。
3. 在设置 → 外观依次点击浅色、深色、跟随系统，再分别选择蓝色和安妮雅；手动模式应立即生效且不被系统覆盖。退出重开后选择仍保留。
4. 首次 0.1.2 正式发布后，安装版点击检查更新应显示已是最新版本。断网检查应出现可重试错误，联网后能恢复。
5. 完整升级需要公开更新源存在比当前安装版更高的正式版本（例如后续 0.1.3）。届时在 0.1.2 内检查，应只提示新版，不自动下载。
6. 点击下载更新，观察进度；下载完成先正常退出并重新打开，版本应仍为 0.1.2。再次检查和下载可复用缓存，点击重启并更新后先选稍后，程序应继续可用。
7. 完成当前编辑并等待保存，确认重启并更新。新版应自动打开，在关于中确认版本已升高，登录、数据、明暗模式及字体偏好仍保留。

没有更高正式版本时只能完成前四步，不能把“已是最新版本”当作完整升级通过。若更新安装未完成，记录关于页状态与报错；当前版本应继续可用，也可手动运行官方新版安装包修复。

## 明暗外观

设置 → 外观提供浅色、深色和跟随系统按钮，与蓝色 / 安妮雅配色独立保存。旧设置默认跟随系统，手动选择不受系统明暗变化影响。偏好仅保存在当前设备。
