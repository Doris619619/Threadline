# Threadline — Codex 全自主开发总 Prompt

你现在负责从当前仓库开始，完整开发 **Threadline**。

Threadline 是一个面向个人的高信息密度时间规划、任务记录、Daily 追踪与长期数据复盘工作台。它不是企业项目管理软件，也不是传统 Todo List。它最核心的目标是：

> **让我能够极其快速地安排今天、看清今天、记录今天，并最终拥有长期、结构化、可分析的个人时间数据。**

请以“可以长期真实使用的正式产品”为标准开发，而不是 Demo、概念验证或静态 UI。

# 2. 产品设计总原则

Threadline 必须始终遵循以下原则。

## 2.1 极简，而不是“功能少”

极简的意思是：

- 高频操作步骤少；
- 页面信息清晰；
- 不出现无意义确认框；
- 不出现为了“高级感”而制造的大量装饰；
- 不使用复杂弹窗打断流程；
- 能直接编辑的地方优先直接编辑；
- 能单击完成的事情不要设计两步。



## 2.2 高信息密度

这是极其重要的产品要求。

Threadline 是每天真正使用的工作台，不是用于展示的 Landing Page。

禁止：

- 巨大的任务卡片；
- 大面积无意义留白；
- 一屏只能看到四五个任务；
- 每条任务占据过高纵向空间；
- 为了视觉“高级”牺牲信息效率。

桌面端首页在常见 1440×900 或类似尺寸下，应尽量让用户**无需滚动即可看到当天绝大多数任务**。

目标：

> 一屏舒适看到约 10～15 条普通任务，同时仍能看到 Daily 区域和顶部核心数据。



## 2.3 Apple 风味，但不要“AI 塑料感”

视觉参考用户提供的最终 UI 图片。

目标关键词：

- Apple-like
- macOS productivity
- Quiet luxury
- 克制
- 轻盈
- 干净
- 精确
- 高级
- 大量浅色
- 非深色主题
- 非赛博朋克
- 非霓虹
- 非渐变堆叠
- 非 Glassmorphism 滥用
- 非“AI SaaS 模板感”

主要视觉：

- 白色 / 非常浅的暖灰或冷灰背景；
- 极轻的层级阴影；
- 浅边框；
- 克制蓝色作为主要交互色；
- 项目标签拥有自己的颜色；
- 大圆角可以使用，但不要过度；
- 控件尺寸偏紧凑；
- 字体层级明确；
- 留白用于区分层级，不用于制造空旷。

不要机械复制 macOS，而是吸收其：

- 克制感；
- 精确感；
- 层级；
- 交互反馈；
- 字体节奏；
- 视觉重量。

- Tailwind CSS
- CSS Variables 设计 Token
- Radix UI primitives（仅用于无障碍、Popover、Dialog 等基础能力）
- Lucide React 图标

可以使用成熟基础组件，但：

> **不允许直接套用明显的 shadcn 默认外观。**

所有核心 UI 应根据 Threadline 自己的 Design System 定制。

建立统一 Token：

- background
- surface
- surface-secondary
- border
- border-subtle
- text-primary
- text-secondary
- text-tertiary
- accent
- danger
- success
- shadow
- radius
- spacing

## 3.3 数据

正式架构采用：

**Supabase + PostgreSQL**

负责：

- 项目
- 普通任务
- Daily 定义
- Daily 每日实例
- Daily 子任务
- 历史
- 收尾记录
- 待安排
- 放弃记录
- 回收站
- 周/月统计原始数据

使用：

- Supabase JS SDK
- PostgreSQL
- RLS
- SQL migrations
- Zod 做输入验证

所有数据库迁移放在：

```text
supabase/migrations/
```

建立：

```text
.env.example
```

不得把 Secret 提交进仓库。

如果开发时没有真实 Supabase Key：

- 不允许因此停止 UI 开发；
- 建立 Repository/Data Access Layer；
- 提供 seed/mock development data；
- 保证之后切换真实 Supabase 时 UI 无需重写。

推荐：

- TanStack Query

负责：

## 3.6 图表

## 3.7 测试

## 3.8 PWA

# 5. Project 项目规则

项目至少包含：

```ts
Project {
  id
  name
  color
  status
  createdAt
  archivedAt?
}
```

状态：

```text
active
archived
```



## 5.1 项目颜色

每一个项目拥有一个固定颜色。

项目创建时：

- 用户自己选择颜色；
- 后续可以修改；
- 所有项目标签统一使用该颜色体系。

标签必须：

- 小；
- 克制；
- 易识别；
- 不抢任务名称的视觉中心。

---



## 5.2 内置项目「其他」

系统必须内置：

```text
其他
```

用途：

- 买转换插头
- 取快递
- 打电话
- 打印材料
- 临时杂事

即使任务不值得建立独立项目，也始终有合法项目归属。

---



## 5.3 项目归档

项目允许归档。

归档后：

- 不进入默认活跃项目选择列表；
- 历史数据全部保留；
- 累计投入保留；
- 任务保留；
- 周/月统计保留；
- 可以恢复归档。

归档 ≠ 删除。

普通任务核心：

```ts
Task {

  title

  date?

  plannedStartTime?
  plannedEndTime?
  plannedDurationMinutes?

  actualDurationMinutes?

  completed
  completedAt?

  status

  postponedFrom?
  postponedTo?

  abandonedAt?

  createdAt
  updatedAt
  deletedAt?
}
```

其中除了：

```text
title
projectId
```

以外，其余时间字段均可选。

# 7. 普通任务 UI 最低形态

Threadline 必须允许极轻量任务。

例如：

```text
□  [其他]  买转换插头
```

它可以没有：

- 开始时间；
- 结束时间；
- 预计耗时；
- 实际耗时。

不要强迫用户补齐信息。

---



# 8. 首页整体布局

最终桌面端首页必须高度参考仓库中的最终参考图片。

布局大致为：

```text

│ 首页                   │ 核心统计                                    │
```

左侧导航固定保留。

# 9. 首页顶部统计

首页顶部必须同时清楚显示：

```text
普通任务       Daily       普通实际       Daily 实际       今日总实际
6 / 12        2 / 4       5h20min        1h10min          6h30min
```



## 9.1 普通任务完成数

```text
6 / 12
```

只统计普通任务。

**绝对不能把 Daily 算进去。**

---



## 9.2 Daily

```text
2 / 4
```

单独统计。

---



## 9.3 三类实际时间

必须分开：

### 普通实际

普通任务累计实际投入。

### Daily 实际

Daily 累计实际投入。

### 今日总实际

```text
普通实际 + Daily实际
```

三者都要显示。

---



# 10. 无时间今日待办

没有具体开始时间的今天任务：

**放在时间轴上方。**

例如：

```text
无时间待办

□ [其他] 买转换插头
□ [生活] 取快递
```

原因：

- 数量一般较少；
- 需要醒目；
- 不应该污染时间轴排序。

设计必须紧凑。

---



# 11. 今日时间轴 / 今日日程

这里是整个 Threadline 的最核心区域。

用户习惯按照时间规划一天。

任务行顺序必须遵守：

```text
时间 → 方形完成框 → 项目标签 → 任务名称 → 预计/实际时间
```

例如：

```text
12:00–13:30   □   [科研]   修改论文      预计 1h30min   实际 55min
```

或：

```text
14:20         □   [AI研究] 跑 Demo      预计 45min
```

---



# 12. 时间定义

首页上的时间：

**是计划时间，不是实际开始时间。**

例如：

```text
12:00–15:00 修改论文
```

意思是：

> 用户计划 12:00 开始做，15:00 结束。

不是软件自动记录真实开始/结束。

---



# 13. 开始时间 / 结束时间



## 开始时间

可选。

## 结束时间

可选。

允许：

```text
14:20
```

只有开始时间。

也允许：

```text
12:00–13:30
```

开始 + 结束。

---



# 14. 时间输入方式

不要使用复杂：

- 时间滚轮；
- 巨大 DateTime Picker；
- 一堆时间按钮；
- 多层弹窗。

用户需要可以直接键盘输入。

例如：

```text
1420
```

自动格式化：

```text
14:20
```

输入：

```text
930
```

自动格式化：

```text
09:30
```

应做：

- 输入校验；
- 自动格式化；
- 非法时间提示。

---



# 15. 预计耗时

如果存在：

```text
plannedStartTime
plannedEndTime
```

系统自动计算：

```text
plannedDurationMinutes
```

例如：

```text
12:00–13:30
```

自动：

```text
预计 1h30min
```

用户不需要再填。

如果只有：

```text
14:20
```

则允许用户手动填写：

```text
预计 45min
```

全部可选。

---



# 16. 实际耗时

实际耗时：

```text
actualDurationMinutes
```

由用户自行填写。

**实际耗时和是否完成必须完全解耦。**

允许：

```text
✓ 已完成
实际耗时为空
```

也允许：

```text
□ 未完成
实际 2h
```

绝对不要：

> 点击完成 → 强制要求填写实际耗时。

---



# 17. 实际耗时输入格式

用户主要输入分钟。

例如输入：

```text
45
```

显示：

```text
45min
```

输入：

```text
90
```

自动显示：

```text
1h30min
```

输入：

```text
150
```

显示：

```text
2h30min
```

固定格式：

## 小于 60 分钟

```text
Xmin
```



## 大于等于 60 分钟

```text
XhYmin
```

不要显示：

```text
90min
```

---



# 18. 完成按钮

这是硬规则。

每个普通任务使用：

**方形 Checkbox**

位置：

```text
时间 后面
项目标签 前面
```

例如：

```text
12:00–13:30  □  [科研] 修改论文
```

完成：

```text
12:00–13:30  ✓  [科研] 修改论文
```

---



## 18.1 点击完成

点击：

```text
□
```

立即：

```text
✓
```

不要：

- 弹 Dialog；
- 询问是否确定；
- 强制填写耗时；
- 跳转页面。

---



## 18.2 可以取消完成

再次点击：

```text
✓
```

恢复：

```text
□
```

不弹确认。

这是高自由度工具。

---



## 18.3 完成后的视觉

完成后：

- 项目标签继续保留；
- Checkbox 保持 ✓；
- 文字适当降低视觉权重；
- 可以轻微变淡；
- 不要强制删除线；
- 任务不能从当天列表消失。

任务完成后仍保留在原时间位置。

---



# 19. 首页排序

有时间任务：

按：

```text
plannedStartTime ASC
```

排序。

允许时间重叠。

例如：

```text
14:00–16:00 A
15:00–16:00 B
```

完全允许。

不提示也可以。

不自动调整。

规则：

> 谁开始早，谁排在前。

开始时间相同：

任意稳定顺序即可。

---



# 20. 不允许拖拽时间轴来修改时间

不要设计：

> 拖到 14:00。

因为用户无法精确知道拖到哪里等于几点。

修改任务时间的方式应该是：

直接编辑：

```text
开始时间
结束时间
```

保存后系统自动重新排序。

---



# 21. 临时任务

必须支持极快创建。

临时任务建立后：

- 如果有今天时间 → 自动进入时间轴；
- 如果今天无时间 → 自动进入“无时间待办”。

创建不要搞复杂 Wizard。

---



# 22. 不存在“进行中”

普通任务不需要：

```text
todo
in_progress
done
```

用户不需要点击“开始”。

核心只有：

```text
未完成
完成
```

再配合其他生命周期行为。

---



# 23. 普通任务生命周期

普通任务支持：

- 完成
- 移期
- 暂不安排
- 放弃
- 删除

这些概念严格不同。

---



# 24. 移到明天 / 未来日期

如果任务今天未完成：

可以选择：

```text
明天
指定未来日期
```

默认推荐“明天”。

但是：

## 今天历史必须保留

例如今天原本：

```text
完成 8/12
```

其中 2 个移到明天。

今天历史仍然：

```text
8/12
```

任务历史记录：

```text
未完成
已移至 8/24
```

不能因为延期就把今天的分母偷偷减少。

---



# 25. 暂不安排

支持：

```text
暂不安排
```

意思：

> 这件事仍然要做，但目前不知道哪天做。

进入：

# 待安排池

---



# 26. 待安排池

待安排只需要两个层级：

```text
重要
不重要
```

不要：

- 高
- 中
- 低
- P0
- P1
- P2

---



## 26.1 重要

可以表示：

- 重要；
- 紧急；
- 应优先处理。

---



## 26.2 不重要

可以表示：

- 不紧急；
- 意义较低；
- 有空再处理。

优先级必须容易修改。

---



# 27. DDL

待安排任务可以设置 DDL。

DDL：

**精确到日期 + 时间。**

例如：

```text
2026-08-28 23:59
```

不是只有日期。

DDL 可选。

没有：

```text
null
```

不要强迫用户填写。

---



# 28. 待安排 → 今天

允许把待安排任务安排到今天。

可以使用拖拽进入今天，也可以按钮：

```text
安排到今天
```

但无论哪种方式：

**不允许降低首页信息密度。**

---



# 29. 放弃

这是非常重要的统计规则。

任务可以：

```text
放弃
```

放弃代表：

> 用户明确决定不再执行这个任务。

---



## 29.1 放弃不算今日任务

例如当天：

```text
原本 12 个
完成 8 个
```

其中一个后来选择：

```text
放弃
```

那么当天有效普通任务分母应减少。

放弃任务：

**不计入今日普通任务完成率分母。**

---



## 29.2 放弃仍然保留历史

虽然不算当天有效任务：

**放弃行为本身必须长期保留。**

历史中应该能查到：

```text
2026-08-23
[科研]
阅读某论文
状态：放弃
```

周/月复盘可以统计：

```text
本周放弃 3 项
```

---



## 29.3 放弃 ≠ 删除

绝对禁止把放弃实现为数据库 DELETE。

---



# 30. 删除

删除只表示：

- 建错了；
- 重复创建；
- 数据本身不应该存在。

删除后：

进入：

# 回收站

---



# 31. 回收站

删除数据进入回收站。

保留：

```text
30 天
```

30 天后：

永久删除。

支持 30 天内恢复。

---



# 32. Daily 的定位

Daily 是一种特殊每日任务模板。

仍然属于某个项目。

例如：

```text
[雅思] 雅思学习
[六级] 六级学习
[GitHub] 发布内容
```

Daily 也必须显示项目标签。

---



# 33. Daily 不算普通任务

绝对禁止：

把 Daily 算进：

```text
普通任务 6/12
```

Daily 使用自己的：

```text
Daily 2/4
```

---



# 34. Daily 每天只计算一次

Daily 一天只有：

```text
完成
未完成
```

同一天不累计多次。

---



# 35. Daily 不允许移到明天

如果 Daily 今天没做：

今天记录：

```text
未完成
```

明天正常生成新一天实例。

禁止：

> 把昨天未完成 Daily 搬到今天。

---



# 36. Daily 子任务

Daily 一般包含重复性的子任务。

例如：

```text
[六级] 六级学习

□ 背单词
□ 听力
□ 阅读
```

右侧 Daily 区域必须清楚展示这些子任务。

不要把子任务藏到深层页面才能看到。

---



# 37. Daily 子任务完成规则

只要今天完成任何一个子任务：

整个 Daily 自动认为：

```text
今日完成
```

例如：

```text
✓ 背单词
□ 听力
□ 阅读
```

则：

```text
[六级] 六级学习 → 今日完成
```

Daily 今天只算一次。

---



# 38. Daily 最外层也可以直接完成

即使没有操作子任务：

用户也可以直接点击 Daily 最外层 Checkbox：

```text
□ → ✓
```

表示今天完成。

---

例如：




# 60. Git Commit 规则

这是强制规则。

## 60.1 高频 commit

每完成一个明确的小功能，就尽可能 commit。

不要：

> 写完几十个文件、五六个功能以后一次性提交。

推荐：

一个小而完整的逻辑：

→ test
→ commit

每一个 Goal 一般应该拥有多个清晰 commit，而不是只有一个巨型 commit。

---



## 60.2 只本地提交

执行：

```bash
git commit
```

**不要自动 push。**

不要：

```bash
git push
```

除非用户以后明确要求。

---



# 61. Commit Message 格式

严格使用 Conventional Commits：

```text
type(scope): 中文描述
```

例如：

```text
feat(home): 实现高密度首页日程布局
feat(task): 支持普通任务完成与取消完成
feat(time): 支持时间输入自动格式化
```
