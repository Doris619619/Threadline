# Threadline 工程协作规范

本规范适用于本仓库中的所有代码、配置、文档与 Git 操作。任何修改前必须完整阅读本文件；如与任务需求冲突，应先说明冲突并取得确认，不能静默违反本规范。

## 1. 文件与函数注释

### 文件说明

每个新建或实质修改的源代码、脚本、配置或文档文件，都必须在文件开头用该格式支持的方式说明“这个文件是做什么的”。说明应简短、准确，并与实际职责一致。

- TypeScript、JavaScript、Rust、CSS 等支持注释的文件：使用文件头注释。
- Markdown：使用 HTML 注释作为首行文件说明。
- JSON 等不允许注释的格式：不得为了满足本规范写入非法注释；应优先使用格式已有的 `description` 字段，或在同目录的 Markdown 说明文件中记录其用途并在变更说明中指出。
- 第三方生成文件、锁文件和框架自动维护文件不应手工插入注释；它们的用途在对应配置或文档中说明即可。

### 函数说明

每个新建或修改的自定义函数、React 组件、Hook、方法和关键回调，都必须在定义前写明：它做什么、输入/输出或副作用，以及任何容易误解的业务规则、边界条件或异步行为。

- 使用该语言惯用的文档注释格式，例如 TypeScript 的 JSDoc、Rust 的 `///`。
- 简单实现可以简短，但不能写空泛的“处理数据”之类注释。
- 注释必须解释意图与约束，不能仅逐字重复代码。

## 2. 职责拆分

禁止将大量不相关的代码堆入一个文件。新增或扩展功能时，必须按清晰的职责边界拆分，例如页面展示、UI 组件、状态/业务逻辑、数据访问、类型定义和工具函数。

如果某个文件同时承担多个独立职责，或继续扩展会显著降低可读性，应先拆分再添加逻辑。拆分应避免为了“文件数量”制造只有一两行、没有独立职责的碎片文件。

## 3. 分支命名

创建分支时必须使用以下格式：

```text
<type>/<YYYYMMDD>-<short-description>
```

其中日期使用创建当天的八位日期，`short-description` 使用简洁的小写英文短语，并以连字符分隔。允许的常用 `type` 为：

- `feat`：新功能
- `fix`：修 Bug
- `ui`：界面
- `refactor`：重构
- `chore`：配置或工程
- `perf`：性能优化
- `docs`：文档
- `experiment`：实验

示例：`feat/20260823-desktop-export`、`fix/20260823-task-ordering`。

## 4. 文档与 README 同步

每一次修改都必须检查并维护相关文档；不允许出现代码已变更、说明仍描述旧行为的情况。

- 面向使用者的命令、安装方式、环境要求、产品能力或目录结构发生变化时，必须同步更新根 `README.md`。
- 设计、架构、需求、接口、流程或开发约定发生变化时，必须同步更新 `docs/` 中对应文档；没有对应文档时，应新增职责明确的文档。
- 纯内部重构如果不改变对外行为，也必须在提交前明确确认 README 和 docs 无需更新，并在提交说明或变更说明中体现这一判断。
- 完成前应复核文档中的路径、命令、截图描述和行为说明是否与当前代码一致。

## 5. 提交与提交前自检

每一次修改完成后都必须创建 Git commit，不能只留下工作区改动或仅口头汇报。提交应只包含同一项完整、可追溯的工作，并使用能准确表达目的的提交信息。

提交标题必须严格使用以下格式，不能省略 `scope`，也不能将全角冒号 `：` 写成半角冒号 `:`：

```text
<type>(<scope>)：<summary>
```

- `type` 只能使用本规范“分支命名”中列出的类型，例如 `feat`、`fix`、`ui`、`refactor`、`chore`、`perf`、`docs`、`experiment`。
- `scope` 必须是本次改动的具体模块或领域，使用简短的小写英文连字符短语，例如 `cloud`、`desktop-build`、`task-list`；不得使用 `misc`、`other`、`update` 等无信息范围。
- `summary` 必须明确描述用户或系统可观察到的结果，使用中文简述；不得使用“更新”“修改”“修复问题”等空泛表述。
- 一次提交只说明一个完整目的；不同目的必须拆分为独立提交。

正确示例：`fix(cloud)：修正ROS2话题与驱动配置`。不合规示例：`fix: 修复问题`、`docs: update readme`、`更新代码`。

仅当用户明确要求“不提交”，或提交被权限、Git hook、冲突等客观问题阻断时，才可以不创建提交；此时必须说明原因、保留工作区，并请求下一步指示。

提交前至少确认：改动遵守本规范；注释与职责拆分完成；README 和 docs 已更新或已确认无需更新；只暂存本次任务的文件；并执行与改动相称的验证。

## 6. Pull Request 正文

创建或更新 GitHub Pull Request 时，正文必须严格遵守 [docs/PR撰写规范.md](PR撰写规范.md)。

- 必须包含并按顺序使用：`Summary`、`背景`、`改动（逻辑）`、`改动（代码）`、`影响`、`验证`、`材料`。
- Summary 写可观察结果；背景写约束与取舍；**改动（逻辑）写用户体验与交互行为，改动（代码）写模块级实现细节**；影响写清边界与副作用；验证写已跑检查与待办；材料附文档与相关链接。
- 禁止只写空泛的一两句摘要，或仅罗列文件名而不解释为什么这样改；禁止把「逻辑」与「代码」两节合并成单一的 `## 改动`。
- 代理代写 PR 时默认套用该文档中的骨架与风格参考，不得另起一套更短、更空的格式。
