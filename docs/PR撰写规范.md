# Threadline PR 撰写规范

创建或更新 Pull Request 时，正文必须按本文件的结构与风格书写，不得只写一两句空泛摘要。目标是让审查者在不翻完整 diff 的情况下，理解**做什么、为什么、怎么改、影响什么、怎么验**。

## 强制结构

PR 正文按以下顺序使用二级标题；某一节确实无内容时，写一句明确说明（例如「无后端接口变更」），不要整节省略到审查者不知道是否遗漏。

```markdown
## Summary

## 背景

## 改动

## 影响

## 验证

## 材料
```

### Summary

- 用 3～6 条短 bullet，概括**用户或系统可观察到的结果**，不要罗列文件名。
- 关键点结论可用 `**加粗**`，其余句子保持克制，不要整段加粗。
- 若覆盖 issue、承接已合并 PR、或本分支是某条线的唯一待审 PR，在 bullet 之后用一两段散文交代关系（编号、合并状态、当前审查重心）。

### 背景

- 说明需求从哪来、约束是什么、为什么现有实现不够。
- 写清关键设计取舍：采纳了什么、砍掉了什么、各自的理由。
- 合规、安全、账号模型、平台限制等「决定实现形态」的事实优先写在这里，而不是埋在改动细节里。

### 改动

- 按模块 / 包 / 目录写清实际落地内容，可点名关键路径与公共 API。
- 解释**非显而易见的命名、分层、并发、鉴权、schema**决策，而不是复述每一行 diff。
- 对容易误读的点主动说明「为什么叫这个名字 / 为什么不放在别处」。

### 影响

- 写清对现有用户、配置、开关、迁移、生成代码、上下游仓库的影响。
- 明确「没有什么」也很重要（例如：无 feature 开关、无新后台任务、不落库某类数据）。
- 若含大范围生成物或顺带 regen，单独说明哪些是噪声、哪些是实质行为变化。

### 验证

- 列出已执行的检查与结果（构建、类型检查、测试、迁移、真实账号联调等）。
- 已完成的用文字或 ✅ 标明；仍需人工 / 上线后确认的用 `- [ ]`。
- 写明验证边界：哪些告警/失败与本 PR 无关。

### 材料

- 链接设计文档、相关 issue / PR、前端或后端配套 PR。
- 有 UI 时附截图或说明「纯后端，无 UI 截图」；有桌面端时说明验收用的安装包/便携版路径（若适用）。

## 写法要求

- 用中文写审查者真正需要的信息；专有名词、API、路径、命令可保留英文。
- 先讲结论与约束，再讲实现细节；避免只有「更新了 XX 文件」。
- 一次 PR 对应一条可审查的主线；若历史演进复杂，在「背景」里交代，不要把无关工作塞进同一 PR 却不说明。
- 不要粘贴大段无关日志；必要命令与结果用短句概括即可。

## 正文骨架

复制以下骨架填写（删除括号提示语）：

```markdown
## Summary

- （可观察结果 1）
- （可观察结果 2）
- （可观察结果 3）

（可选：与 issue / 前序 PR / 本线唯一待审 PR 的关系。）

## 背景

（需求来源、约束、为何决定当前实现形态；砍掉的方案及理由。）

## 改动

- **`path/or/module/`**：（做了什么、关键 API / 行为、非显然决策。）
- **`...`**：（……）

## 影响

- （对用户 / 配置 / 数据 / 生成代码 / 依赖方的影响）
- （明确无影响的边界，如无新开关、无后台任务等）

## 验证

- （命令或检查）✅ / 结果简述
- （真实环境或端到端）……
- [ ] （仍待上线或人工确认的项）

## 材料

- 设计文档：`docs/....`
- 相关 issue / PR：……
- （截图或「无 UI 截图」说明）
```

## 风格参考（结构示意）

下列示例展示的是**信息密度与段落组织方式**，不是 Threadline 业务内容；撰写本仓库 PR 时套用同级结构与深度，替换为本次真实改动。

```markdown

- 用户在对话内**搜索 / 阅读 / 总结自己的邮箱**：不后台轮询、不落库邮件正文，需要时才实时查 Microsoft Graph。
- 每个用户可连**多个**邮箱……
- 三个只读工具 ……；无 feature 开关时，没连邮箱的用户看不到这些工具。

原 PR #N 已合并进本分支……本 PR 现在是这条线的唯一待审 PR。覆盖 issue #M。

## 背景

……约束决定了实现形态：
- **不落库邮件正文**——……
- **……跑不通**——所以数据模型变成……

演进过程中砍掉的两层，理由相同：……

## 改动

- **`internal/service/.../`**：……公共 API：……
- **主账号语义**：……
- **Schema**：……

## 影响

- **无 feature 开关**：……
- 只读、on-demand……
- `gf gen dao` 顺带重生成了其余表：哪些是噪声、哪些是实质变化……

## 验证

- `go build ./...` ✅ / ……
- [ ] 上线验：……

## 材料

- 设计文档：`docs/....`
- 前端 PR：……
- 纯后端，无 UI 截图
```
